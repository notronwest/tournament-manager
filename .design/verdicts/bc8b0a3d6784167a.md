## Findings

1. **web/src/pages/public/PublicTournamentPage.tsx:749 (computed) → :3047–3067 (rendered) → #11** — the cost
   line in the register form quotes the *payer's* price tier, not the chosen registrant's.
   `entryCostTier` is derived once per page from `myStatus`, which holds only the signed-in
   player's own registrations, and is handed to every `EventCard` (`:1291`) and rendered
   unchanged no matter who the "Registering for" chooser names. Observed at 390 and 1280: Maya
   already holds a pending Kids-bracket entry, yet opening Open Doubles with "Registering for
   Maya Harper" states "**$45** entry · includes this event", while the checkout — which the
   same change correctly re-tiers per registrant — prices that row as the +$15 additional event.
   The mirror case is worse money: a parent who has already paid for one event sees "Extra
   event: **+$15** (added to your registration)" on a child's *first* event, which checkout and
   `compute_checkout_total` will charge $45 for. Fix: compute the tier from the chosen
   registrant's own active registrations (the card already receives `dependentEventIds`) and
   word it for that person rather than "your registration" / "your entry" (#6).

2. **web/src/pages/public/PublicTournamentPage.tsx:2559 → #15** — the new age gate's refusal is a
   dead end on a condition the player can fix. `checkEligibility` now emits "needs a date of
   birth on file" (web/src/lib/eligibility.ts), and the card renders it as a grey 12px line with
   no next move and no link — six lines above, the same block already turns an unset gender into
   "Set your gender to register →" (`:2553`), which is the pattern this case needs. The copy that
   would help ("Add your date of birth on your profile") exists only inside the register form,
   which this player can never open, because the Register button is replaced by that grey line.
   Same shape for a parent who lands on a juniors bracket with nobody on their family list: the
   screen says only "Not eligible: needs age 18 or under" and never mentions that the product can
   now register their child. Fix: extend the gender-unset treatment — link to
   `/profile?return=…` with "Add your date of birth to register →", and name the add-a-child path
   when the event is age-capped below the player.

3. **web/src/pages/admin/AttendeesPage.tsx:170–184 → #13** — the new sub-lines break the attendees
   row at phone width. Measured at 390×844: the Name cell is **85px wide and 152px tall**, and
   "Registered by Dana Harper" renders as "Registered / by Dana / Harper" over three lines, with
   "11 years old" over two. At 1280 the same cell is 306px and reads on one line each — the exact
   "perfect on desktop" failure `docs/DESIGN_PREFERENCES.md` records as a failure to learn from
   (the `EventCard` meta line that "wrapped one character per line"). Fix: stack the table into
   cards below ~700px, or put the guardian line where the layout already stacks (the Contact
   cell) / render it as a compact chip instead of a sentence in an 85px column.

4. **web/src/pages/public/ProfilePage.tsx:899 → #16** — the only entry point to the whole feature
   is below the fold and nothing at the top admits it exists. Measured at 390×844: "My family"
   heading at y=1123 and the "Add a child" button at y=1321, on an 844-tall viewport whose first
   screenful ends in the rating pickers; the page lead ("Anything you update here flows into
   every event you've registered for") names neither this section nor Account. Standing at the
   top, a person cannot list what this page lets them do. The tournament page offers no second

   with a line that names the sections and jumps to them, or lift "My family" above the profile
   form. (Account was already below the fold before this change; this adds the third hidden
   section and the one that gates a new capability.)

5. **web/src/components/ConfirmModal.tsx (reached from ProfilePage.tsx:1198) → #7** — the remove

## Notes (non-blocking)

- **Two panels that contradict each other.** On a blocked registrant with "I need a partner"
  chosen, the red "You can't enter this event: needs age 18 or under" sits directly above the
  amber "We'll register you for this event without a partner." The red one wins (Save is
  disabled), but the stack reads as a question. Suppressing the partner-mode explainer while the
  registrant is blocked would settle it.
- **"Pick someone else above" can be fruitless.** On the kids bracket with the child already in,
  the only other name in the chooser is the parent, who cannot enter it. "Ask the organizer" is a
  real next move, so this clears #15, but the first instruction offered is a loop.
- **Hand-rolled notice styles beside the ones the theme exports.** `subjectBlockedStyle`
  (PublicTournamentPage.tsx:3346) re-implements `statusPanelStyle("danger")` with a different
  border, and `subjectAlreadyInStyle` (`:3334`) uses raw `#eff6ff` / `#bfdbfe` / `#1e3a8a` where
  `publicTheme` exports `infoBg` / `infoBorder` / `infoFg`. That hex trio already appears
  elsewhere in this file, so it is consistent with the file and inconsistent with the theme —
  worth collapsing, not a blocker. Contrast measured 9.5:1, fine.
- **Unreachable validation copy.** ProfilePage's "A first and last name are both needed." and "A
  date of birth is needed so age-restricted brackets can check it." never render: all three
  inputs carry `required`, so the browser's native bubble fires first. Either drop the dead
  branches or drop `required` and own the messages.
- **No confirmation after a removal.** Adding a child shows a success panel; removing one shows
  nothing — the row simply disappears. The disappearance is visible feedback, so this clears #3,
  but the two halves of the same card now behave differently.
- **Wording.** "Registering **Maya Harper**" on the checkout review card reads as a fragment
  ("For Maya Harper" / "Entrant: Maya Harper" would sit better), and "needs age 18 or under" is
  machine phrasing carried into user-facing copy (the reason string predates this change).
- **Three filled CTAs now on one profile page** (Save profile · Add a child · Update password).
  Each sits in its own form and the new one is inside its own card, so #2 holds per card; flagged
  only because the page was already at two.
- **The standard is silent on one thing (D-0018):** whether a page-level derived value (here, a
  pricing tier) must be recomputed when a chooser changes whose data the surrounding form is
  about. Finding 1 is graded under #11 because the visible result is a wrong number; a sharper
  rule about "every value in a form is about the subject the form names" would catch the class.
