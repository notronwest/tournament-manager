  tappable above the fold.

  both surfaces it lands on.

  stranded: it is the only filled element in the card and sits left-aligned at the row's
  head with the text link beside it, which is exactly the arrangement it had before when

## Notes (non-blocking)

- **The both-pills state still puts two filled buttons in one card (#2).** Rendered at
  375 px by cloning the pill in the DOM (no data touched): two identical dark pills side
  by side, contact link wrapped below, no overflow. Strictly #2 wants one filled button
  per card. It is **pre-existing**, identical to what is on `main`, and this change only
  ever *removes* filled buttons — it cannot create the pair. Not blocked here, but the
  pair is worth retiring on its own card: the header's filled weight competes with the
  red Register button that is the page's actual task.
- **`Contact organizers →` becomes the only interactive element in the header card when
  both pills are hidden**, at 114 × 20 px (`PublicTournamentPage.tsx:1118-1128`). It clears
  #7's D-0225 carve-out — 13 px, 6.2:1, supplementary context rather than the task, with
  Register reachable through the 46 px Events tab in the first screenful — but the carve-out
  is written for "a text link inside a line of dense metadata", and in this state it is a
  line of its own. Read generously, deliberately. A ≥ 44 px hit area on that link would
  remove the question entirely, and is cheap.
- **Nothing needs to say "times coming soon", because the page already says it twice.**
  The caller asked whether the absence is worse than an explanatory state. It is not: the
  Events tab prints "Start time to be announced" under every event without a time
  (`PublicTournamentPage.tsx:2995-3003`), and the Results tab is always in the tab strip
  and carries "No results yet — scores appear here as games are played."
  (`PublicTournamentPage.tsx:4293`). Both are one tap from the first screenful, verified at
  375 px. Adding a disabled pill or a placeholder would be a third copy of the same
  sentence in a louder place.
- **The header pill and the in-page Results tab answer the same question with different
  thresholds (#10).** `ResultsSection` renders as soon as any match row exists
  (`anyMatches = ms.length > 0`, `PublicTournamentPage.tsx:4289`); the pill waits for
  `in_progress`/`completed`. A generated-but-unplayed draw therefore shows 0–0 standings in
  the tab while the pill is hidden. Not a contradiction a player would catch, and the
  pill's threshold is the better one — but the two surfaces should eventually share it.
- **The page's loading state is the string "Loading…", not a skeleton (#3).** Pre-existing
  and untouched. Noted only because it is what keeps this change honest: the single gate is
  why the new conditions cannot cause a late header shift.
- **No test covers the three header states.** `web/e2e/` has no reference to either
  button, so the repo's own mobile audit would not catch a regression in either condition.
  The commit message records a manual check at 375 px for all three.
