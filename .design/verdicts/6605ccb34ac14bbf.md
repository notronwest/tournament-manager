**All four of the author's claims are true as stated, and I measured each.**
Three identical refusals in a row each pull themselves fully into view; the
row-level panels pull again; a refusal no longer outlives the tab it happened
on; and the counter passes lint and typecheck where `Date.now()` did not.

**The FAIL is that the first two of those are true only within one visit to
the page.** The attempt counter is a `useRef` — it resets to 0 every time the
page mounts — while the set that remembers which pulls have been spent is
module-level and never resets. So the keys of the *next* visit collide with
the keys of the last one, and the first refusals after coming back to the page
do not pull. That is the same defect the seventh verdict found, with the
message swapped for a number that is not unique either. And the new tab-switch
clear destroys a refusal that arrives *after* the switch, so a refused save can
now report nothing at all.

## Findings

1. `web/src/components/PlatformFeeEditor.tsx:336` (`const pulled = new
   Set<string>()`, module scope) against
   `web/src/pages/admin/PlatformSettingsPage.tsx:127` (`const attemptRef =
   useRef(0)`, component scope), with the keys built at
   `PlatformFeeEditor.tsx:282` and `PlatformSettingsPage.tsx:863` → **#3**
   (error state) and **#16** (nothing you can act on sits below the fold) —
   `attemptRef` restarts at 0 on every mount of the page, but `pulled` lives
   for the whole page load, so a refusal on a later visit reuses a key already
   marked spent and does not scroll itself into view. The collision runs as
   deep as the shorter of the two visits: one refusal before leaving means the
   first refusal after coming back is suppressed. Measured at 390 × 844 with
   every PATCH intercepted and answered 406, `getBoundingClientRect` throughout:

   - **First visit.** Refusals 1, 2 and 3, each fired from `scrollY` 0 with
     the Save button at 788–833: all three pulled to `scrollY` **142**, panel
     at **704–788**, the whole message and the audit line below it in view
     (`390-default-third-identical-refusal-pulls-into-view.jpg`). This is
     exactly what the author claims, and it holds.
   - **Then an in-app round trip** — `/admin/platform` → `/admin/site` →
     `/admin/platform`, no reload, the page remounting and `attemptRef`
     returning to 0.
   - **Second visit.** Refusals 1, 2 and 3, each from `scrollY` 0: `scrollY`
     ends at **72** every time and the panel at **773–858** in an 844
     viewport. 72 px is Chrome's scroll anchoring taking up the slack as the
     page grows, not the pull — the pull lands a panel at 704–788 because of
     the 56 px scroll margin, and it did so four taps later. The closing
     sentence, *"ask a platform admin to make the change."*, is the part under
     the edge
     (`390-default-first-refusal-after-spa-round-trip-no-pull-clipped.jpg`).
   - **Refusal 4 of the second visit** — the first attempt number the earlier
     visit never reached — pulls: `scrollY` **142**, panel **704–788**. Three
     suppressed then one restored is the key collision, not a coincidence.

   Successes are unaffected: their keys carry an ISO timestamp with
   milliseconds, which is unique across mounts. → **Fix**: make the token
   unique for the life of the page, not for the life of a mount. A module-level
   counter the component reads once (`const attemptRef = useRef(nextAttempt())`
   over a module `let n = 0`, bumped per save) does it; so does seeding the ref
   from `performance.now()` if the purity rule allows a ref initialiser. Any
   token works as long as no two refusals in one page load can ever share a key.

2. `web/src/pages/admin/PlatformSettingsPage.tsx:495–503` → **#3** (error
   state), **#9** (no silent outcome) and **#15** (a terminal state names the
   next move) — the tab's `onChange` clears all three error slots
   unconditionally, so a refusal that lands *after* the operator has left the
   tab is written into state nothing is rendering, and is then thrown away the
   moment they come back to that tab. The save reports nothing: no refusal, no
   confirmation. Measured at 390 × 844 on the Tournaments tab, with the
   intercepted PATCH delayed 2.5 s: tap "Save fee", switch to Default, wait
   5 s (the 406 lands during that wait), switch back to Tournaments —
   `/wasn't saved/` is absent from the whole document, and the row sits open
   with the operator's draft of 3.00 against an unchanged 3 %
   (`390-tournaments-refusal-destroyed-by-the-tab-round-trip.jpg`). The row's
   own refusal is deliberately rendered outside the `open` guard
   (`:859–866`) precisely so a late answer still reaches the operator; a tab
   change swallows the same answer. → **Fix**: clear only a refusal that has
   been on screen — mark it seen when its panel mounts and clear seen ones on
   a tab change — or clear only the tab being left and let a refusal that
   arrives afterwards survive, dated, which is what the standing note about
   an undated stale refusal was asking for anyway.
